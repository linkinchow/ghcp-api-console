# 用户池推理超时验证工具

本目录用于在隔离环境中验证推理超时、客户端取消以及长请求期间的用户池租约保护。入口为 `run.py`，探针为 `probe.mjs`。详细执行结果与边界见[推理超时验证报告](../../docs/user-pool-inference-timeout-validation.md)。

## 验证对象

- 新配置 `POOL_INFERENCE_TIMEOUT_SECONDS` 的范围为 **5–600 秒**；未配置时回退到旧的 `POOL_REQUEST_TIMEOUT_SECONDS`。
- 推理超时是进程级设置，不纳入共享用户池配置指纹，因此旧、新进程可以使用不同推理超时并连接同一个测试 MySQL 用户池。
- 长请求进行期间，in-flight hold 应阻止已到期租约被旧进程释放；成功、超时及客户端取消结束后均须清除 hold。
- 成功请求续租，失败请求不续租；单次请求只发起一次上游调用，不进行透明重放。

## 运行条件与隔离约束

实际执行面向 **Linux 上的 Docker 环境**，使用已存在的旧、新 Proxy 镜像和测试依赖镜像。工具不负责安装依赖、创建云资源或发布正式镜像。

- 只使用本次运行创建的内部网络、随机命名的测试卷及容器；不发布宿主机端口。
- 使用真实测试 MySQL、模拟上游和预热测试成员，不连接生产数据库、真实模型或 GitHub。
- 仅清理本次运行拥有的资源，保留执行报告及证据；清理结果与请求断言需要分别检查。
- 使用已有镜像不等于完成镜像的全量源码构建验证。正式部署前仍需单独构建、发布并核对待部署镜像。

## 使用方式

从仓库根目录执行静态自检，并先查看当前脚本支持的参数：

```bash
python3 tests/user-pool-timeout/run.py --self-check
python3 tests/user-pool-timeout/run.py --help
```

`--self-check` 用于工具自检，**不能替代实际长请求验证**。实际隔离运行使用 `--execute-isolated-test`，旧、新镜像及其他必要参数以当前脚本的 `--help` 为准；不要将生产资源作为测试参数。本文不假设镜像已存在于读者的机器上，也不把命令示例视为已执行结果。

实际执行应产生包含请求耗时、模拟上游调用与断开、租约/hold 断言以及清理状态的报告。核查报告时应同时确认：

1. 旧、新 Proxy 为不同进程，并共享同一测试 MySQL 用户池。
2. 租约确实在请求运行中自然到期，旧进程仍持续通过存储/释放 API 检查，而非仅在请求结束后检查。
3. 超时与客户端取消传播到模拟上游；每个请求只有一次上游调用。
4. 所有请求结束后 hold 被删除，成功续租、失败不续租。
5. 本次创建的资源清理成功，证据文件仍保留。

## 已完成的真实长请求场景

本轮以四个预热模拟成员、**预绑定的 60 秒 ACTIVE 租约**执行 Messages SSE 请求，不是 300 秒 provisional 租约；没有通过修改时间戳来加速真实长请求。

| 场景 | 请求观测耗时 | 模拟上游观测耗时 | 结果 |
| --- | ---: | ---: | --- |
| 客户端在 5 秒取消 | 约 5 秒 | 4.965 秒 | 取消传播 |
| 旧进程 120 秒超时 | 120.002 秒 | 119.988 秒 | 按旧阈值中断 |
| 新进程长请求成功 | 350.022 秒 | 350.001 秒 | 成功完成并续租 |
| 新进程 600 秒超时 | 600.005 秒 | 599.975 秒 | 按新阈值中断 |

流量阶段共 **601.714 秒**。请求期间持续调用旧进程存储/释放 API，验证 hold 在 60 秒租约自然到期后仍提供保护；所有 hold 最终清除，失败不续租，无重放且每请求一次上游调用。

首次夹具初始化因 MySQL binlog 场景缺少创建触发器所需权限而失败，发生在旧进程启动之前。仅对新建测试 MySQL 增加 `--log-bin-trust-function-creators=1` 后重新执行成功；不要据此修改生产 MySQL 配置。

## 不应外推的结论

- 本轮真实长请求仅覆盖 **Messages SSE**，未执行 350 秒长 JSON 请求，也未验证 owner 故障转移。
- 三个推理端点的路由单测不等同于三个端点都做过真实长请求测试。
- 原生 `fetch` 的独立响应头等待超时可能在约 300 秒触发。这是源码分析发现的边界，不是本轮静默响应头实测结果；**600 秒是应用层最大值，不保证上游静默 600 秒仍可等待**。
- 客户现场 Kubernetes 滚动更新、连接排空及正式镜像发布不在本轮验证范围内。
