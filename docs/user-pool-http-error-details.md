# HTTP 错误详情：范围、使用与验证

日期：2026-09-18。分支：`feat/request-error-details`，从 `main` 的 `de387347702ddaec3c522992c1649348fa6c7bb8` 创建，**不包含 NGINX 功能分支**。本次不部署客户环境、不改数据库schema或账号池配置指纹。

## 1. 本次解决什么问题

原来 Request Stats 经常只有 `HTTP 400`，用户需要另找日志才能判断具体原因。新版对推理转发阶段收到的非成功HTTP响应，保存一段有边界的错误摘要：

```text
HTTP 400: 'max_tokens' must be greater than 0 (code: invalid_parameter, type: invalid_request_error) [ref: <UUID>]
```

这是格式示例，不是对某次客户错误的原因判断。具体内容只来自当次上游已经返回的错误，不猜测、不补造。

- 适用常见上游400、401、403、429、5xx等非成功HTTP响应。
- 读取已捕获的响应，不重复读取/请求上游，不改变发给LiteLLM的原响应正文、状态码、Retry-After、模型名兼容处理、流式转发或重试策略。
- 保留原池完成判定和租约行为。token-count本地估算回退仍可成功，不因为其上游诊断产生额外失败推理统计。
- 保存到已有 `proxy_request_stats.failure_reason`，DTO仍为 `failureReason`，无需新字段或数据库迁移。
- 旧数据不回填。历史记录只有HTTP状态时，新Console仍原样显示，不能还原从未保存的原因。

## 2. 摘要提取及隐私边界

仅从完整、未截断、最多 **16KiB** 的响应捕获中提取：

- JSON的 `error.message`、`error.code`、`error.type`，以及常见的简单字符串error或受限顶层错误封装。
- 非2xx SSE中第一个可识别的JSON错误事件；最多解析64个事件块，整个有界捕获必须可解析。
- 不遍历任意 `details`、请求/响应payload或嵌套对象来寻找“看起来像原因”的字符串。
- 缺失、HTML、纯文本、畸形JSON/SSE、非法UTF-8、过大或截断响应，回退到 `HTTP <status> [ref: <UUID>]`，不把原始正文贴进统计。

摘要总长度最多 **512个Unicode码点**，包含关联ID；先脱敏，再截断，不截断成半个字符。

无论完整诊断日志的脱敏开关如何，统计摘要都会独立处理：

- 已知的入站/出站鉴权、API key、Cookie值、内部密钥，以及URL中的凭据/敏感查询值。
- 常见GitHub PAT、`sk-` token、JWT、Authorization文本、URL和邮箱。
- 控制符、换行及方向控制字符。
- 引号/反引号中的原始数据片段；只保留常见参数名/路径供解释校验原因。
- code/type只接受保守、短小的标识符。

已知敏感值采用去重、有限数量/总长度和单次匹配替换，避免短值反复替换 `[redacted]` 造成膨胀。

**这不是通用DLP保证。** 未知、不带任何特征且未加引号的秘密或业务文字，无法仅凭文本可靠识别。因此页面仍应仅对授权管理员开放，摘要也按运维数据保管，不公开粘贴。对于更严格的数据策略，应单独定义可展示错误码/模板；本次未自动启用完整诊断采集或关闭脱敏。

## 3. 关联ID怎么用

`[ref: UUID]` 复用这次 `recordHttpFailure` 产生的 `diagnosticId`，用于关联Proxy结构化日志的 `upstream-http-error` 事件。

- 有完整诊断且写入成功、未被轮转时，可用同一ID核对诊断记录。
- 采集关闭、写入失败、日志等级过滤、文件轮转或未接集中日志时，详情不一定可查。
- **关联ID不是“诊断文件已保存”的承诺**，Console不把它伪装成可点击的文件链接。
- 这不是统一的入站request ID，也不是所有重试/网关层共用的追踪ID。多副本运维仍需要按时间、实例和该ID检索相应日志。

## 4. Console 如何使用

Request Stats的Failure列从只显示一行截断文字改为：

1. 默认紧凑显示完整存储字符串的CSS缩略预览。
2. 点击行内展开控件或键盘Enter，查看完整**已保存摘要**；文本可以选择，长历史记录可滚动查看。
3. 点击复制图标，复制整条failureReason，不复制省略号。
4. 剪贴板成功反馈约2秒自动清除；失败时提供完整只读文本框手动复制。
5. 包含ref时显示“关联服务器日志，不一定有已保存诊断文件”的提示。

该表格也用于Dashboard失败列表和账号详情，所以共用组件同步生效。不使用HTML渲染上游文本；类似 `<script>` 的历史文本按普通文字展示，不能执行。窄屏在表格区域水平滚动，不把页面整体撑宽。

## 5. 本次没有覆盖的“所有错误”

本轮先交付**推理转发收到的上游非2xx HTTP错误摘要**，不能描述为所有故障均已统一定位：

- 鉴权失败、部分请求验证和账号池准入错误可能发生在请求统计之前，没有账号也不应为了统计而创建账号。
- HTTP200中携带错误/不完整流的语义失败，继续沿用原有完成判定和摘要，本次未统一为新的详细错误事件。
- 连接失败、DNS/TLS、请求总时限、客户端取消、数据库错误等继续使用既有路径，本次不把内部SQL/堆栈直接展示给客户端。
- `/v1/models` 拉取失败和token-count估算回退有各自既有行为；不把本次摘要覆盖范围外推到它们。
- 未新增错误列表分页、长期审计存储、全链路追踪或诊断保留策略。

后续如需全错误来源/统一request ID，应独立设计兼容性和隐私边界，而不是抓取所有原文。

## 6. 客户升级边界

获得完整功能需要分别更新 **Proxy 和 Console**：

- 新Proxy开始保存更具体的failureReason；旧Console通常仍能显示字符串，但默认截断，需要悬停/旧方式查看。
- 新Console可读取旧Proxy的统计格式，并展开/复制原有文本；不会自动补全历史HTTP400。
- 不改MySQL结构、不改配置指纹、不重新开户，不需要为本功能更新SSO/Login或LiteLLM Hook。
- 所有Proxy更新前，同一张统计表可能混有旧状态摘要和新详细摘要，属于兼容期正常情况。
- 保留原管理员数据卷、Secret、后端地址和统计保留量。`REQUEST_STATS_PER_ACCOUNT_LIMIT` 默认每账号2条仍不变；需要更长历史时另行评估，不随本功能悄悄扩大保留量。
- Proxy发布须遵循已有请求排空流程；不要仅为启用错误详情中断长流或直接重建所有副本。

本功能通过独立分支 `feat/request-error-details` 交付，构建镜像时应固定该分支中已验证的完整提交SHA，不依赖浮动分支名。本次仅发布源码及测试报告，不合并main、不部署客户环境。
