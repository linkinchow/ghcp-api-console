## 3/5副本验证边界

副本是独立Node进程、独立缓存和数据库连接池，不是同一进程多监听端口。先使用现有隔离测试VM，不新建资源；同一VM的3/5进程不等于Rancher跨节点或可用区HA验收。仅有限并发与正确性验证，不宣称客户吞吐量。

## 明确不包含

- 多日稳定性与客户真实流式容量，需要确定时长、负载和独立授权，不用短时mock替代。
- 客户生产故障演练、真实GitHub/模型调用、SSO环境改动或新增付费席位。
- SQLite专属失权恢复：客户拟迁移MySQL，暂缓且不作为本轮前置项。
- 为通过测试修改任期、SQL预算、重试或凭据fence。若发现生产缺陷，保留失败并独立说明最小修复。

## 已执行记录

### A：旧进程暂停与恢复——通过

- v5源码未改，Linux真实SIGSTOP并读取procfs确认停止状态；真实MySQL任期到期等待30.092秒，未修改数据库时钟/owner行。
- SIGCONT恢复旧进程时，成员行的其它fence仍相同，但旧owner对应的真实SQL checkpoint返回false且数据完全未变；旧本地任期只记一次`local_tenure_expired`并退为standby。
- 新owner采用原task/nonce，Login POST严格1次，warmup1次，最终Ready；旧进程保持存活standby并检查多轮不再执行旧步骤。
- 1个实际测试通过，0失败/0skip，34.808秒。回调是合成repository层，不是生产HTTP回调路由。
- 日志SHA-256：`30f2cf6e424eabe854e04e3a05c498c35b459da5cee6c9a7731e7f7397df9766`。

### B：Login网络故障——两个实际场景通过，早期夹具失败保留

- 首轮在2.207秒停止：测试worker正常断开IPC时被夹具无条件`exit(2)`判为异常；父进程也可能在读取已排队的`stopped`确认前先看到退出。尚未进入120秒网络超时阶段，TAP的2fail包含一个子场景和父包装，第二子场景未执行。
- 修正只涉及测试：正常关闭受`closing`保护，退出等待要求确认消息且退出码0，仍拒绝无确认、非零、信号退出和fatal消息；新增3个确定性退出竞态测试，合计6离线测试通过，类型检查通过。
- 原失败完整日志SHA-256：`a7b8242c9ff59c28a26061f876d87ddf43549973c8271eabc8150d29ba0daa56`；未删除或覆盖。
- 修正后的第二次运行通过正常退出，但3.071秒时夹具尝试用普通update恢复disabled成员被拒绝，仍未完成120秒场景。此失败保留（SHA-256：`48ededc5067c644188b9fe0d3040eac35cde1b849d81b1292091ce29a17c4046`），后续已核实并改用受支持的操作员恢复路径，不放宽生产状态保护。
- 已确认普通`updateTx`禁止更新任何disabled行；受支持的操作员`retry()`会保留warmup阶段并更新attempt/generation。测试已改用该API并检查新attempt，首个卡住成员的nonce/任务/槽位保护不变。修正版类型和6离线回归通过，随后真实复跑两个子场景均通过，含父包装TAP3pass/0fail/0skip，140.659秒。完整日志SHA-256：`9c30f7ee4149d8f16b529dc259d1e8054d0f74eee509f79d9a6e604eb3e9f8d6`。
- 实际成功数据：静默GET连接在119902.194ms关闭，未发送任何响应头；生产观察耗时119946.020ms，原120000ms配置未改，原因`provision_timeout`。期间worker仍owner且失权计数0，无关warmup先完成，排除提前失权导致的假超时。
- 超时子场景127.895秒、模拟服务重启子场景12.758秒。两者各自Login POST仅1次；任务成功观察释放槽位仍保留failed状态，只有显式operator retry后warmup1次并最终Ready。重启保留的是测试父进程IPC任务账本，不是实际Login持久库/浏览器验收。
- 运行超时清理已改为直接执行测试父进程，SIGTERM后预留30秒清理再强制结束；不改变生产120秒请求预算或数据库任期。

### C：路由复跑通过，首轮失败保留

- 原两项基线通过；新全消费者取消用例通过（2.307秒），验证每个独立缓存最后消费者取消后真实上游连接关闭，hold排空，后续请求不清缓存即可恢复。
- 两个401-first用例都在第282行未验证成员准入断言失败：预期503、实际429。此前旧401/200不改新凭据、不续租及无重放的断言均通过；该错误码差异随后按下述真实准入路径核实，没有宽松接受任意4xx。
- 已对照`admitTx → reclaimMemberTx → updateTx → availableMember`核实为测试预期错误：两个旧hold都排空后，未验证成员被标记failed/warmup、generation推进并回收旧lease；无可用成员时准确返回429 `pool_exhausted`。原仍有live hold的基线才保留绑定并返回503 `member_unavailable`。
- 修正版检查精确429/error code、failed/warmup、`credential_not_verified`、generation仅+1、旧lease删除和唯一过期事件、hold0以及完全不触达上游；原旧响应fence与warmup检查不放宽。修正版本地类型/4离线guard通过，随后真实MySQL复跑**5pass/0fail/0skip，12.612秒**，全部子进程退出、五个随机库清理。
- 修正版完整日志SHA-256：`5b433f6955dea962cb6badb80f12624a53bcfcfb48481c0f9092cc03e41b3ce8`。
- 合计3通过、2失败、0skip，12.320秒；五个子进程对均退出、五个随机库均清理。
- 首轮日志SHA-256：`2a3483dc3438a8a8d33321e3d9e42a2b3f622e03923354d5356226fbaeaed66c`。
