## 2. 调度模型结果

**最终16项通过，0失败。** 这是设计公式的可执行例子，不调用应用源码、不连接SQLite/MySQL、不启动SSO/Login/Proxy。

| 场景 | 实际断言结果 |
| --- | --- |
| 空池cap500/300/200、target50 | 登记库存25/15/10 |
| cap相等，库存80/20，缺10 | 10次登记均给B，变为80/30 |
| 全局idle20≥target10但企业失衡 | 不登记新账号 |
| idle2、pending3、target10 | 只新增5个；再次调度不重复登记 |
| TTL释放40个账号 | 库存不变，idle充足时不补建 |
| A80/B20，idle5/2 | 新绑定依次B、B、A；总库存仍80/20 |
| 所有企业达到cap | 不补建，但已有idle仍可绑定 |
| 首选企业临时不可建 | 下一合格企业承担全局缺口 |
| A100/idle20，新B库存0，target10 | 初始不建；11次消耗后只给B登记1个 |
| target0 | 不补建，现有idle仍可出租 |
| A库存100、cap降到50 | 不删除/继续增加A；缺口给其他企业 |
| failed/disabled等占用库存 | 不从cap计数中忽略，也不能因此给满cap企业继续建号 |
| 排空企业持有大量idle | 不把禁止新分配的idle用来掩盖active企业的备用缺口 |
| target高于全部cap合计 | 恰好在各cap处停止，不突破 |
| 区分比例缺口与cap利用率 | cap600/300/100、库存50/23/27时，比例缺口选A；最小N_e/C_e会选B，故不能混用算法 |
| 区分当前与前瞻占比 | cap9/1、库存1/0时，建号按当前占比选B，不用(N+1)前瞻公式继续选A |

模型采用稳定ID作为平局顺序，便于重现，**没有验证生产平局散列/轮转的长期分布**。模型中的pending是预先给定的抽象值，未验证实际任务状态分类、恢复时限或MySQL/SQLite集合一致性。

本地模型及原始输出保留在忽略的 `.claude/multi-enterprise-scheduling-model.py` 和 `.claude/multi-enterprise-scheduling-results.json`，不是发布运行组件。正式实现必须将这些场景转成仓库内自动测试，并增加数据库、并发和跨服务用例。

## 3. 代码核对带来的重要修正

### 已确定并写入设计

- **一套SSO原生多profile**，不采用每企业独立SSO的折中拓扑。后者会延续用户希望消除的运维数量问题。
- 使用库存**占比缺口**排序，不用单独weight、每企业idle或N_e/C_e替代；全局库存达标时不为平衡额外开户。
- 绑定不改变总库存，因此无需为了精确库存比例把所有新caller放进全局租约锁；仍需保证caller/member的并发安全。
- 已有lease及catalog hold固定关系优先于企业比例；冷却/401/失败不触发跨企业重试。
- 归属覆盖Proxy主账号、SSO用户、Login任务/回调，而非只增加Console企业下拉框。
- 现有名称目录是共享10000位置，不是每企业10000；不改旧identity/ordinal或重用已消耗名字。
- 新增schema_version不能让旧binary自动拒绝；SQLite及旧direct路径尤其需要维护停写和访问隔离。
- SAML单例、会话pending槽、用户名自动匹配、URL前缀判断均需真正租户化，不是挂多个路径就安全。
- 旧profile-less入口只兼容default；保持default原SSO公开URL/entityID/签名身份，不能把旧入口动态切到别的企业。
- Login取消/重启失败不证明外部浏览器任务已结束，回调/账号世代和nonce必须继续fence。

### 文档复核与修正

- 首稿建号用了(N+1)前瞻缺口、绑号用了N的当前缺口。复核指出这与“唯一一条当前占比标准”不严格一致；已统一为N×C_e−C×N_e，空池仅首个登记按cap优先，并增加cap9/1、库存1/0的区分用例。先前15项仅证明旧模型内断言通过，最终统一模型16项重新执行全部通过。
- 首稿没有明确catalog hold与企业draining交界。已规定只有catalog hold、没有lease时，排空企业拒绝新建推理lease，已有catalog执行可结束，不能跨企业替换；该规则尚待应用测试，不计入算术模型通过项。

### 研究建议的取舍

Console/运维研究提出“每企业单实例SSO”作为降低改造量的备选，并将N_e/C_e作为候选算法。主方案明确不采纳这两点：前者不符合本次减少服务套数的目标，后者不完全等价于已讨论的目标占比差。文档保留的是主会话统一后的方案，不能把并行研究的备选当成额外已批准需求。

## 4. 本阶段没有做的验证

- 没有修改运行时代码、数据库schema、配置文件或客户数据。
- 没有运行新的Proxy/SSO/Login/Console单元回归、类型检查、生产构建或浏览器验收：本阶段没有这些代码变更。
- 没有运行MySQL事务/锁竞争、双后端一致性或多Proxy并发测试。
- 没有迁移实际SQLite/MySQL，也没有验证新的迁移/降级工具；工具尚未实现。
- 没有真实SAML登录、GitHub/SCIM/席位/模型调用，没有新建Azure资源。
- 没有验证费用、吞吐、容量或固定时间比例收敛；算术模型不能证明这些结论。
- 没有扩大既有10分钟/半小时测试授权，未来端到端活动需要单独有界安排。
