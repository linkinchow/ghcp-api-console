# 生产 MySQL User Pool：推理总时限从120秒提高到600秒

**状态：本提交包含独立推理时限覆盖，448项Proxy回归通过，Azure真实旧120/新600共库长流验证通过。未发布客户镜像；旧镜像不能直接使用新参数。以下操作要求从包含本改动的固定源码提交构建并核对新Proxy镜像。客户K8s排空/切换仍需按实际平台执行，不能据本测试承诺零中断。**

核对日期：2026-09-17。代码基础 `80e8315`；仅聚焦600秒，不扩展一小时、不取消超时、不增加基于流空闲时间的另一套机制。

## 一、结论与推荐

**推荐新增“仅推理请求超时覆盖”的兼容版 Proxy，保留原配置和 MySQL 指纹不变，采用蓝绿或受控逐副本切换。** 不推荐为了这次调整先停全部服务、改数据库指纹。

新版本使用：

```dotenv
# 保留客户当前实际旧值，不在本次变更中修改：
POOL_REQUEST_TIMEOUT_SECONDS=120
# 新版新增，仅控制真实模型推理请求：
POOL_INFERENCE_TIMEOUT_SECONDS=600
```

**第二项仅包含本次改动的新版本支持。旧镜像不会因此获得600秒能力。** 使用固定源码构建并核对新镜像后，按下文操作；已完成的实际测试和未覆盖的客户环境边界见第十一节及测试报告。

预期影响：

- 不迁移MySQL，不UPDATE指纹，不清理账号/租约/统计，不重新开户。
- 只更新Proxy；SSO、Login、Console不需要为此重建镜像或停机。
- LiteLLM业务地址、原K8s Service名称/IP/端口不变。
- 新旧Proxy可同时服务同一个池，前提是混合版本验证全部通过。
- 已经在旧Proxy执行的请求仍是旧时限，不会中途变为600。
- 目标是降低业务中断风险，不承诺现有入口能力未知时零中断。

**本方案取代此前“直接修改旧参数并离线迁移指纹”的首选建议。** 那条路径技术上可另做工具，但会带来停机窗口、远程数据库维护和回退复杂度，不适合客户此次优先降低业务影响的目标。

## 二、为什么要加独立参数，而不是直接改原参数

旧 `POOL_REQUEST_TIMEOUT_SECONDS` 有三类用途：

1. 推理与目录请求的绝对总时限。
2. 请求hold的持久化截止时间。
3. 后台预配/HTTP步骤的预算。

它还参与 `config_fingerprint`。直接设600不仅影响推理，还会改变后台预算并导致现有MySQL指纹不匹配。只改HTTP计时器也不够：hold仍按120到期，心跳会把长请求中断。

新参数必须独立于 `PoolConfig`，不能随手添加到被整体展开计算hash的对象里；否则即使旧参数仍为120，也会意外改变指纹。

## 三、开发设计与当前实现

### 3.1 配置契约

新增 `POOL_INFERENCE_TIMEOUT_SECONDS`：

- 不配置时回退到旧 `POOL_REQUEST_TIMEOUT_SECONDS`，保持兼容。
- 严格校验5–600秒，0、空串、非法格式均不作为无限等待。
- 仅部署端设置，不接受客户端header、请求正文或metadata覆盖。
- 启动读取，当前不设计热加载；在途请求保留起始时捕获的有效时限。
- 不进入旧池指纹、不改数据库schema，不改变旧配置解析和完整性检查。
- 启动日志只输出非敏感有效时限，并明确区分推理、旧目录/预配预算；不输出凭据。

### 3.2 只影响哪些请求

| 请求 | 新版行为 |
| --- | --- |
| POST `/v1/messages` | 新推理时限600秒 |
| POST `/chat/completions` | 新推理时限600秒 |
| POST `/responses` | 新推理时限600秒 |
| GET/HEAD `/v1/models` | 保留旧预算120秒及内部模型缓存刷新限制 |
| POST `/v1/messages/count_tokens` | 保留旧预算120秒 |
| Worker预配、Login任务观察、预热 | 保留原配置，不随新推理参数改变 |
| direct路由模式 | 不启用此User Pool覆盖行为 |

### 3.3 时限必须贯通HTTP与hold

在真实推理准入开始时取得一次有效600秒预算：

- 准入中止计时器使用该预算。
- `acquire(caller, signal?, requestTimeoutMs?)` 增加向后兼容的可选参数，未传时仍使用旧store配置。
- MySQL和SQLite只将本次预算传到推理hold创建，不能修改共享store.options。
- hold使用数据库时钟记录绝对 `deadline_at`，`expires_at` 仍为deadline加既有10秒清理宽限。
- HTTP剩余计时扣除准入已花费的时间；持续收到流数据不延长总截止时间。
- 保留5秒心跳、generation/nonce/owner围栏、取消、失败不续租、完整成功才续租和不确定COMMIT不重放。

### 3.4 混合版本为什么有可行基础

现有旧代码的heartbeat、reclaim、currentHold和释放检查使用**每条hold已保存的截止时间**，不会拿本机120秒重新计算别人的hold。所以旧worker/Proxy有能力看到并保护新600秒hold，而新代码也不能延长旧120秒hold。

这是源码核对结论，必须以真实旧镜像＋新镜像共库测试证明后才可上线。不能仅据设计推理跳过测试。

### 3.5 明确不改的保护

- MySQL连接获取、锁、事务等共享SQL预算仍为5秒，不变为600。
- owner租约和续约机制不变；后台调度不拆分、不新增leader。
- 池最大账号数、idle target、正式租约TTL、临时租约TTL、账号凭据全部不变。
- 原模型缓存刷新还有独立约30秒预算；上游原生传输可能另有限制，不能承诺完全无响应一定能等满600。
- 进程退出保护不在本次自动延长；通过上线前排空控制已有25秒强制关闭风险。

## 四、客户需要知道的行为变化

### 4.1 600秒仍是总时限

开始请求后，最多允许执行到600秒；第590秒还在输出也不会重新计时。未发响应头时到期返回504，已经流式输出时中止连接。已输出部分内容的请求可能已产生上游用量，不能自动重放。

### 4.2 临时租约默认300秒不等于在途请求只能300秒

新caller的首次请求超过300秒时，有效600秒hold仍保护该成员不被其他caller抢走，原请求可以继续并在成功结束后转为正式租约。

但同一caller在首次请求超过300秒、尚未完成时再发请求，可能收到503 `lease_draining`。本次不顺便修改临时TTL；这是上线前必须让业务方知晓并测试的行为。

### 4.3 更长请求会占资源更久

- 最坏情况下连接、在途请求记录和成员占用持续更久。
- 请求所在进程崩溃且无法清理时，hold可保留到记录的deadline加10秒；不是600秒后一定还挂着，而是故障清理的最长边界变大。
- 该成员有有效hold时，凭据修复/重分配会受到保护限制。

## 五、上线前必须完成的验收

**以下为发布门槛，不是已经完成的测试结果。**

1. 配置单测：未配置完全兼容；600有效；0/超范围无效；新参数不改变旧fingerprint；其他旧不变量继续严格校验。
2. 真实MySQL混合版本：旧120、新600同时启动、重启、轮流成为owner，均不改已有指纹。
3. 长hold跨版本：新600请求在旧worker回收、旧Proxy查询/释放/并发准入时不被提前回收，不出现重复分配。
4. 实际长流：持续输出超过120及300秒但小于600，完整成功并续租；并行验证取消及时释放、失败不续租、旧请求仍120。
5. 实际600秒截止：未完成mock流到600秒被中断，hold正确清理，无自动重放；不能只用缩短时钟单测代替。
6. SQL预算仍5秒，同caller队列隔离、401/generation变化、不确定提交与迟到结果保护回归通过。
7. LiteLLM→Proxy→mock的实际Messages/Chat/Responses及JSON/SSE验证，排除外层提前超时；目录/count_tokens不被新参数改变。
8. 按下文部署/回退操作演练，实际长流在排空过程中不被误杀。

测试只用隔离数据库和合成上游，不需要客户生产账号。最终交付包含固定源码SHA、新Proxy镜像digest、实际报告和本手册的可执行版本；未达到以上门槛时不得让客户试着直接改现网。

### 6.2 安全与备份

虽然本方案不修改数据库schema/指纹，生产发布仍应确认最新备份可恢复，保留原Deployment/Service/HPA/ConfigMap配置及镜像。

### 6.3 外层超时核对

为支持600秒总推理，业务SDK和LiteLLM若设有更短总时限，必须另行调整到覆盖该预算并留传输余量；具体字段按客户实际版本核对，不盲用通用环境变量名。

NGINX模板的 `proxy_read_timeout=300s` 是相邻上游读操作的空闲上限，不是300秒总时限。持续流可以超过300秒；完全无数据超过300秒仍会被NGINX先断开。首token等待、上游fetch、入口/网关也可能有独立限制。本次首先解决正常长输出被120秒截断，不保证完全无响应也必定等满600秒。

## 七、推荐上线：新Deployment并存、原Service不变

### 步骤1：提前启动新版本，不替换旧Pod

从原Deployment复制**已核对的**发布配置，使用新的Deployment名称和不与原Service匹配的标签。新旧均连接同一个原MySQL数据库，旧配置保持原值，仅新版本增加拟实现的覆盖项。

新Pod的示意片段如下，**不是现在可直接应用的完整YAML**：

```yaml
metadata:
  name: <new-proxy-deployment>
spec:
  replicas: 1
  selector:
    matchLabels:
      app.kubernetes.io/name: ghcp-proxy-timeout600
  template:
    metadata:
      labels:
        app.kubernetes.io/name: ghcp-proxy-timeout600
    spec:
      containers:
        - name: proxy
          image: <已完成600秒验证的新Proxy镜像digest>
          env:
            - name: POOL_INFERENCE_TIMEOUT_SECONDS
              value: "600"
          # 其余envFrom、Secret、资源、探针、卷及旧参数完整沿用原部署。
```

新环境不修改 `POOL_REQUEST_TIMEOUT_SECONDS`。如果旧值并非120，必须按实际旧值保留，不能在复制配置时恢复默认。

**状态检查**：新Pod `/readyz` 正常且 storage=mysql；无fingerprint冲突；原账号/租约数量符合正常业务变化；新旧数据库指纹未发生人为迁移。新Pod可能参与worker选举，这是原有多副本行为，只有通过混合版本验证才可允许。

### 步骤2：独立管理通道验证新Pod

原Service继续服务旧Pod。使用临时port-forward或隔离测试Service访问新版本，验证版本/有效超时和少量已批准业务请求。

```bash
kubectl -n <namespace> port-forward deployment/<new-proxy-deployment> 18000:3000
```

```bash
curl --fail http://127.0.0.1:18000/readyz
```

不要临时关闭鉴权或使用真实长请求反复重试。实际600秒行为应已在上线前mock环境验收，生产只做批准的小范围验证。

### 步骤3：先保证新组容量，再切原Service

需要新组能够承担预计流量，数据库允许新旧并存连接量。例如旧3个、新3个、每个10条，阶段上限为60条应用连接，另留余量。

通过原配置管理流程将**原Service的完整selector**替换为新组标签。保留Service对象名称、ClusterIP和端口，不删除重建。切Service不会自动把原HPA指向新Deployment：切换前须给新服务组配置对应HPA/副本上下限，或在发布窗口固定足够副本；旧排空组禁止HPA自动缩容，避免提前终止长请求。回退时要反向恢复这些目标及上下限，不能只恢复Service selector。所有更改应通过原Helm/GitOps控制方式完成。

若要分批试点，必须由已存在且已验证的上游选路能力实施；普通Service混放新旧Pod不是精准百分比灰度，也不能保证每个用户立即得到600秒预算。

切换后检查EndpointSlice只包含新组Ready地址。旧Deployment暂时保留，不立即scale0。

### 步骤4：确认旧连接排空，再删除旧Pod

**这是最重要的生产操作边界：**改变Service selector只影响新连接的后端选择，已有TCP/HTTP keepalive可能继续连接旧Pod并发起新请求。不能等固定120秒就假定旧Pod已经无流量。

优先使用客户实际入口/SDK已支持并演练过的能力：

1. 不再给旧连接派发新请求；已有响应继续读取。
2. 轮换/关闭已空闲的上游连接池，不强行关闭活动流。
3. 从请求日志/入口在途连接指标确认旧Pod不再接新请求，最后在途请求结束。
4. 再通过发布流程把旧Deployment缩为0；控制HPA/GitOps避免旧副本重新拉起。

当前Proxy收到SIGTERM后约25秒会强制关闭剩余HTTP连接。因此**不能先删除Pod再等待600秒，也不能只调大terminationGracePeriodSeconds**。

如果客户现有入口不支持可靠摘流和连接轮换，选择下述短维护窗口，或继续保留旧Pod直至能安排窗口；不要为了追求“零中断”强行终止未知活动流。

### 步骤5：结束观察

确认旧Pod停止、新组处理全部新请求、没有指纹错误/异常重试/新401/hold异常，长流不再在120秒处被截断。保留旧发布文件和镜像用于回退，不立即删除。池设置/补池状态按原策略保持，不需要为了这次兼容升级全局暂停开关。

## 八、缺少无损摘流能力时的最小维护窗口

提前把新组启动并验证完成后：

1. 暂停向这套Proxy提交新请求；优先在客户已验证的网关入口短暂排队，否则明确返回可重试的维护响应。当前软件没有自动提供这种队列，不可假定存在。
2. 等待旧组所有活动请求完成。旧总时限120秒只是参考，必须确认实际流量已停、hold/连接已排空，不是盲等固定秒数。
3. 将原Service改指已Ready的新组，确认EndpointSlice；关闭旧组空闲连接并停止旧Pod。
4. 恢复入口，少量请求验证后正常放量。

这种方式有一个短暂暂停新请求的窗口，但不需要停止MySQL/SSO/Login/Console，也不需要迁移业务数据。实际窗口由在途请求和客户端连接管理决定，不能承诺固定几十秒。

## 九、回退操作

本方案保持原fingerprint/schema，不需要反向SQL迁移。

### 尚未切流

原组仍正常服务，摘除并排空新组测试请求后停止新Deployment即可。

### 已切流，新组出现问题

1. 若旧组已缩为0，先用原镜像和原完整配置启动，确认Ready、指纹正常及有承载容量。
2. 将原Service完整selector恢复为保存的旧值；新组保留执行已有600秒请求，不立刻终止。
3. 按同样连接轮换/排空流程让新组退出，最长在途请求可能接近600秒。若发生严重安全/数据问题必须立即强停，明确记录可能截断请求，禁止自动重放。
4. 确认后停止新组；撤销新覆盖配置时也必须通过Pod发布流程。

**流量回退不等于worker回退。** 新Pod在排空期间仍可能持有共享池owner；切Service不会转移或关闭它。如果故障只在推理路径，可保留新Pod完成安全排空；如果是worker或共享状态异常，需要明确选择等待安全排空还是紧急终止，并接受可能截断在途请求。不得手工改owner/hold。恢复完成还必须确认健康的旧版本worker已经取得正常owner并继续后台处理，且HPA的目标和缩容保护已正确恢复。

不得删除数据库里的600秒hold、改截止时间或恢复旧库快照。即使新进程故障，旧代码也应按持久化deadline保护/回收这些hold，此兼容性必须上线前实际验证。

## 十、验收与停止条件

### 成功条件

- 原数据库/schema/fingerprint不变，原凭据、成员、租约及历史没有人为清理。
- 新版本实际推理预算600秒，旧目录/预配预算不变；普通SQL仍5秒。
- 已完成真实混合版本及120/300/600边界验收。
- 客户入口、连接池和Pod排空流程经过确认，明确是否需要短暂停接。
- 错误率、延迟、连接/hold数量在客户已批准范围；不存在同caller跨成员重复分配。

### 立即停止扩大范围

- 新Pod指纹/schema初始化错误；不能通过改数据库解锁。
- 短请求失败率升高、连接数/内存异常、hold无法释放、401修复异常。
- 仍在120秒截断且确认落在新Pod：检查实际生效配置和剩余外层限制。
- 无法判断旧Pod是否仍接收请求：保持旧Pod，不继续删Pod。
