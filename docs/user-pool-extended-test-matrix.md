# User Pool 扩展场景验收矩阵

日期：2026-09-15。对象：`ghcp-user-pool-mysql` 未提交候选。继0→2000发现调度堵塞并修复后，按“状态转换×并发×故障时点”补充验证；不把测试数量或单次通过称为穷尽所有问题。

## 历史失败与已完成的恢复验证

第一次建池中途退出owner的严格无错runner失败：退出前501Ready，接管后504Ready；1个mock授权回调失败，任务标记`local_callback_failed`，无SCIM冲突/新增失败成员，Proxy已恢复、Worker暂停、现场保留。该runner原本要求所有开通副作用都成功，因此不能用它证明故障后的重试恢复。

新增独立的保留现场恢复验证，不修改原无错验收：允许已明确终态失败的这一次授权使用新nonce重试，但严格禁止同identity+nonce重复POST、重复SSO/SCIM/seat、额外未计划回调失败、槽位超限或直接改Ready。只有同一成员最终重新授权并warmup、全2000Ready及跨副本canary完成才算该恢复路径通过。另补确定性“回调写入前失败／已提交但确认丢失”回归，区分安全重试和真正的数据一致性缺陷。

## 已完成的扩展结果

- **故障后的原现场恢复通过**：504Ready继续到2000Ready，467.841秒；2001Login任务=2000success+1已知callback失败，每identity/nonce只POST一次。旧无错failover测试仍失败，不冒称无中断建池；恢复后2个canary标记在保存的mock记录中唯一且同成员。未额外新增SCIM用户或席位；当前seat计数不统计幂等重复HTTP调用，不作更强声明。
- **慢Login对照通过**：120成员、每任务1000ms，Login1用128.313秒、Login5用48.514秒；各120任务/成功回调、无失败或槽位超限、最终排空及4次跨副本canary通过。这不是实际浏览器性能结论。
- **热caller阻塞/取消通过安全断言**：两个Proxy共32同caller请求+2其它caller，主动取消16个。持锁1.5秒时其余18个200；持锁6.5秒时其余18个在约5.05秒返回503，取消/失败请求未达上游、迟到hold排空、恢复探针成功、无重放/锁泄漏。
- **当时的可用性发现（已在后续修复）**：长锁阶段另一个caller的2个探针也503，说明一个热caller可占满共享数据库连接。后续caller-isolation-v4增加获取连接前的有界caller队列，严格复测B由约4.91秒变为23/31ms200；详见[caller隔离报告](user-pool-caller-isolation.md)。全库/多caller过载不由此保证隔离。
- **确定性回调歧义回归通过**：写入前失败、已提交但确认丢失两种情况均经新nonce恢复原成员；旧成功/失败回调不能覆盖或撤销新凭据。该检查点Proxy327pass/0fail/5DBskip；后续存储错误修复后为375tests/368pass/0fail/7条件skip，类型检查通过。

新增MySQL生命周期契约、旧调度镜像14阶段HTTP生命周期均已通过。实际MySQL重启发现即时连接错误映射缺陷，修复产品及夹具后第三轮完整通过；最新`storage-error-v3`镜像30分钟soak完整通过：1807秒、5083请求、0意外错误、最终hold0，详见[完整报告](user-pool-extended-test-report.md)。

## 范围与安全边界

仅现有隔离Azure测试资源、全新具名测试卷和随机MySQL测试库。真实Proxy/SSO/MySQL，SCIM/席位/Login完成/模型均mock；禁止真实GitHub、客户环境或付费席位。本机Docker保持关闭，不commit/push、不删除旧卷。每场景记录候选镜像、配置、断言、实际结果及清理；故障只作用于固定测试项目。

## 2026-09-15 恢复执行检查点

公司策略关机后用户授权开机，两VM已运行；旧测试容器未自动启动，mock内存及`/tmp`合成配置丢失。保留旧数据库卷，创建新fixture，合成配置迁到持久测试目录。首次启动因缺失empty.env失败属于夹具恢复失败，不是业务断言；已修正恢复脚本。

生命周期runner的预执行复核纠正了401租约预期：故障令旧租约过期，hold排空后删除；修复原成员不会自动建立caller租约。六个原租约只要求保持到主动全池401注入前，恢复后验证新排他租约，不将新leaseID冒称原lease。该改动仅修测试，不修改产品契约。
